# KUROKO デモ動画用スライドの素材

> この文書は、Gemini の Canvas で Google スライドを作るための**入力**です。スライドごとに「見出し・伝えること・本文・使う図・話す内容」を書いてあります。図は `docs/demo/figures/export/` の PNG（16:9）を貼ります。元の図は `docs/demo/figures/*.drawio`（draw.io で直せます）。
>
> 作成日: 2026-10-12。数字と文言は、実装と [SPEC.md](../SPEC.md)・[submission.md](../submission.md) に合わせてあります。**実装と違うことを足さないでください**（末尾の「言い方の注意」）。

## Canvas への頼み方（そのまま貼れます）

```
下の素材から、3分のデモ動画に挟む Google スライドを作ってください。
- 16:9。1スライド1メッセージ。文字は少なく、大きく。
- 色は、紺（#141D2E）を基調に、強調は黄（#F8C450）と緑（#12A594）。背景は白か生成り（#FBF9F4）。
- 「使う図」があるスライドは、図を大きく置き、見出しと1〜2行だけを添える（図の中の文字と重複させない）。
- 「話す内容」は、スピーカーノートに入れる。
- 素材に無い機能・数字・固有名詞は足さない。
```

## スライド 1: タイトル

- **見出し**: KUROKO — 飲み会の幹事を、舞台裏で引き受ける AI エージェント
- **サブ**: お金まわりまで任せられる。ただし、AI はお金に触れない。
- **話す内容**: 会社の歓送迎会の幹事の仕事を、依頼から入金の確認、振り返りまで引き受ける AI エージェントです。

## スライド 2: 課題

- **伝えること**: 幹事の仕事でいちばん面倒なのは、お金まわり。
- **使う図**: `KUROKO_スライド_01_課題.png`
- **本文（図に無い補足は不要）**
  - 按分に、会社の規程が絡む（役職ごとの割合・主役は0円・新人は軽減・会社の補助）
  - 承認と証跡が要る
  - 集金がなかなか終わらない
- **話す内容**: 幹事には、出欠、店探し、予約、立替、割り勘、承認、集金と、用事が次々に来ます。とくにお金まわりは、会社の規程が絡み、承認の証跡も要ります。いまの割り勘サービスは、金額を幹事が決めて入力する前提で、ここは担ってくれません。お金まで任せたい。でも、AI にお金を触らせるのは怖い。ここが出発点です。

## スライド 3: KUROKO がすること

- **伝えること**: 依頼から入金の確認・振り返りまで。人は、確かめて、同意・承認するだけ。
- **使う図**: `KUROKO_スライド_02_KUROKOがすること.png`
- **話す内容**: 幹事は Web のチャットで依頼します。KUROKO は、出欠と支払いの委任を集め、全員が帰りやすい店を提案し、領収書を読み取って規程どおりに按分し、承認を取り、振込を依頼して、銀行の明細で入金を確認します。最後に振り返りを集めて、次回に活かします。

## スライド 4: 設計の中心 — AI は、お金と個人情報に直接触れない

- **伝えること**: 役割の境界そのものが、いちばんの安全策。
- **使う図**: `KUROKO_スライド_03_役割の境界.png`
- **本文**
  - AI：聞く・探す・調べる・説明する
  - コード：計算する・検査する・署名する・動かす
  - 人：確かめる・同意する・承認する
- **話す内容**: AI が担うのは、聞く、探す、調べる、説明する、までです。金額の計算、承認者や支払先の決定、署名、振込は、決まった手順のコードが行います。AI のツールに、お金を動かすものはありません。AI の出力だけでは、お金は動きません。必ず、コードの検査と、人の確認・承認を通ります。

## スライド 5: デモの前提

- **伝えること**: 架空の会社の、10人の歓送迎会。画面に出て操作するのは3人。
- **使う図**: `KUROKO_スライド_06_デモの前提.png`
- **本文**
  - 株式会社Akakura・第一開発チーム（すべて架空）
  - 幹事（Web）／赤坂 くらお（一般）／赤くら 花子（部長・承認者）
  - 領収書 49,500円 → 会社の補助 30,000円 → 按分の対象 19,500円
- **話す内容**: デモは、架空の会社の10人の歓送迎会です。幹事は Web、参加者のくらおさんと、承認者の花子さんは Slack と銀行で操作します。銀行は、GMOあおぞらネット銀行の銀行 API の実験用の環境で、資金は仮想です。

## デモ（画面の録画。75秒の目安）

実演用の画面 <https://kuroko-509311.web.app/demo> で撮ります。手順と期待値は [e2e_scenario.md](../guides/e2e_scenario.md)。待ち時間（店の検索・銀行の承認・入金の確認）は、編集で詰めます。

| 順 | 映すもの | 画面の字幕（例） | 見せたい点 |
|---|---|---|---|
| 1 | チャットで依頼 → 計画を確定 | 自然文で依頼。計画は、幹事が確かめて確定 | 幹事の確認（Human-in-the-loop） |
| 2 | 「部長と新人の負担はどう違う？」 | エージェントが規程を調べ、「第4条」を添えて答える | エージェントが自分で判断してツールを使う |
| 3 | Slack：くらお・花子が「参加して、委任に同意する」 | 上限額・支払先・期限つきの委任（AP2 の委任状） | 鍵1：本人の委任 |
| 4 | 「店の候補を出す」→ 店を選ぶ | 全員の帰りやすさで順位。前回の実績（記憶）つき | 順位はコード。Memory Bank の活用 |
| 5 | 予約画面・領収書をアップロード | 読み取った値を、幹事が確かめて確定 | AI が読み、人が確かめる |
| 6 | 按分の内訳 | 部長 4,800円／一般 2,100円／新人 1,000円／主役 0円。根拠は規程 第4条 | 計算はコード。根拠が出る |
| 7 | Slack：花子が「この按分を承認する」 | 承認できるのは、規程で決まった承認者だけ | 鍵2：按分の承認 |
| 8 | 銀行（sunabar）で、2人が振込を承認 | お金を動かす最後の一押しは、口座の持ち主 | 鍵3：銀行での本人承認 |
| 9 | 入金の確認 → 完了 | 銀行の明細で確認できたときだけ「完了」 | 明細での確認 |
| 10 | 振り返り → 「次回に覚えさせる」 | 決まった形の文だけを、記憶に保存 | 経験の蓄積 |

**デモ中に一言で言えると効く文**

- 「金額を計算したのは、AI ではなく、決まった手順のコードです」
- 「1円でも委任の上限を超えたら、振込は作られません」
- 「銀行の明細で入金を確認できたときだけ、完了にします」

## スライド 6: エージェントがすること

- **伝えること**: エージェントは、自分で判断して、調べて、説明する。ツールは4つだけ。
- **使う図**: `KUROKO_スライド_05_エージェントがすること.png`
- **本文**
  - 規程の検索／店の検索／予算の確認／イベントの概要
  - 入口と出口は、Agent Gateway と Model Armor で検査
  - 記憶は Memory Bank。保存するのは、幹事が確かめた、決まった形の文だけ
- **話す内容**: エージェントは Agent Runtime で動き、ツールは、自分たちの API が MCP で公開する4つだけです。規程を聞かれると、自分で判断して規程の文書を調べ、条番号を添えて答えます。「振込先を変えて」と言われても、変える道具がそもそもありません。

## スライド 7: 実運用に耐える設計 — 3つの鍵

- **伝えること**: 3つの鍵がそろわないと、振込は成立しない。検査は二重。
- **使う図**: `KUROKO_スライド_04_3つの鍵.png`
- **本文**
  - 鍵1 本人の委任（AP2 の委任状）／鍵2 按分の承認／鍵3 銀行での本人承認
  - 請求する側と支払う側が、互いを信用せず、別々に検査する（Policy Gate）
  - 口座とトークンは、銀行の窓口のサービスだけが持つ
- **話す内容**: 権限は AP2 の委任状で決め、送金は銀行 API で行います。請求を作る側と、支払う側を別のサービスに分け、それぞれが検査します。二重の実行を防ぐ仕組みと、期限切れの作り直しも入れています。

**ここで足せる補足（時間があれば、1枚に）**

- 状態を進めるのは「事実」だけ（出欠が出そろった・領収書を確定した・入金を明細で確認した）
- Slack の操作は3秒以内に受け付けて Cloud Tasks に流し、処理は冪等
- 支払いの識別子は「イベント × 支払う人」で決まるので、再送しても二重の振込にならない
- 自由記述は、ツールを持たない別のエージェントが、決まった語彙にだけ落とす（隔離抽出）

## スライド 8: 構成

- **伝えること**: エージェントは Agent Runtime、お金と鍵を扱うコードは Cloud Run。分けてデプロイし、権限を分ける。
- **使う図**: `KUROKO_スライド_07_構成図.png`
- **本文（使った Google Cloud のサービス）**
  - Agent Platform：Agent Runtime（ADK・Gemini）、Agent Gateway、Model Armor、Agent Registry、Memory Bank
  - Cloud Run ×5、Cloud Tasks、Cloud Scheduler、Firestore、Cloud Storage、Cloud KMS、Secret Manager、Firebase
- **話す内容**: エージェントと、決定論的なコードを、デプロイ単位で分けています。外部の API のキーと銀行のトークンは、エージェントには渡していません。

## スライド 9: まとめ

- **見出し**: お金まで任せられる。ただし、AI はお金に触れない。
- **本文**
  - 依頼から入金の確認・振り返りまでを、1つのエージェントが引き受ける
  - AI は、聞く・探す・調べる・説明する。計算・検査・署名・振込は、コードと本人
  - 審査員の方は、Web だけで最後まで体験できます：<https://kuroko-509311.web.app>
- **話す内容**: 審査員の方は、Google アカウントでログインするだけで、Slack も銀行の口座もなしに、最後まで体験できます。

## 言い方の注意（スライドと字幕で守ること）

| 言わない | 代わりに言う |
|---|---|
| 実際のお金が動く | 実在の銀行 API で、依頼から入金の確認まで実行する（資金は仮想） |
| AP2 で送金する | AP2 の委任状で権限を決め、送金は銀行 API で行う |
| 全員が Slack と銀行で操作している | Slack と銀行を実際に操作するのは2人。ほかの5人は、デモ用の代行（検査と署名は、全員ぶんが同じコード） |
| AI が間違えても絶対に安全 | AI の出力だけでは、お金は動かない。コードの検査と、人の確認・承認を通る |
| 規程を RAG で検索 | エージェントが、ツールで規程の文書を条ごとに調べる |
| エージェントが記憶を読む | 記憶（Memory Bank）は、コードが読み書きし、店の順位と理由に使う |
| 攻撃をブロックする | Model Armor は、いまは検知して記録する設定。お金は、コードの検査で守る |

- 会社・規程・登場人物・予約画面・領収書は、すべて架空です。
- 店の候補は、実在の店が出ます。「前回の実績」は、デモ用に入れた架空の記録です（映すときは、その旨を字幕に入れるのが安全です）。
- 本番で使うには、制度面（電子決済等代行業の登録など）の確認が要ります。

## プロジェクト概要

（200〜300文字。下の文は 232 文字）

KUROKOは、会社の歓送迎会の幹事業務を舞台裏で引き受けるAIエージェントです。幹事がWebで依頼すると、Slackで出欠と支払いの委任を集め、全員が帰りやすい駅で店を提案します。開催後は領収書を読み取り、会社の規程に沿って按分し、承認者の承認と各自の委任の範囲内で、銀行APIで振込を依頼して入金まで確認します。AIが担うのは、聞く・探す・提案する・説明することだけです。金額の計算、可否の判断、署名、振込は決定論的なコードが担い、AIはお金に直接触れません。

## プロジェクト紹介

### 課題と解決

**課題: 飲み会の幹事は大変。とくに、お金まわりが面倒**

会社の歓送迎会の幹事を任されると、仕事の合間に、小さな用事が次々に発生します。出欠の確認、全員が帰りやすい店探し、予約、当日の立替、会計のあとの割り勘の計算、承認の取り付け、集金の声かけです。

なかでも面倒なのが、お金まわりです。

- **按分に、会社の規程が絡む。** 役職ごとの負担割合、主役（歓迎・送別される人）は0円、入社1年未満は軽減、会社の補助の上限。幹事は、規程を読んで手で計算し、その根拠を全員に説明します。
- **承認と証跡が要る。** 誰が按分を承認したのかを、あとから示せる必要があります。
- **集金がなかなか終わらない。** 立て替えたお金を、1人ずつ声をかけて集めます。

既存の割り勘・集金サービスは、集金と領収書が中心です。金額は幹事が決めて入力します。**規程に沿った判断と、承認の証跡までは担いません。**

**解決: 依頼から入金の確認まで、お金まわりも含めてAIエージェントが引き受ける**

KUROKO は、面倒なお金まわりまで引き受けます。それでも安心して任せられるように、**AIそのものは、お金に触れない**作りにしました（くわしくは、下の「設計の中心」）。

| 段階 | KUROKO がすること | 人がすること |
|---|---|---|
| 依頼 | 幹事の自然文（「来週金曜の19時、8人で渋谷で」）から、計画を作る。足りない情報は質問する | 幹事が Web で依頼し、計画を確定する |
| 出欠・委任 | 参加者に Slack で、出欠と「上限額・支払先・期限つきの支払いの委任」を聞く | 参加者がボタンを押す |
| 店 | 参加者の最寄り駅から、最も遠い人の所要時間が短い駅を選び、周辺の店を提案する。**選んだ理由**を添える | 幹事が店を選び、予約する（予約の代行はしない） |
| 精算 | 領収書の写真を読み取り、規程に沿って按分する | 幹事が読み取り結果を確かめて確定する |
| 承認 | 規程で決まる承認者に、按分の内訳を Slack で送る | 承認者が承認する |
| 送金 | 委任の範囲内で、銀行APIに振込を依頼する。期限切れは作り直す | 本人が銀行で振込を承認する |
| 入金確認 | 幹事口座の入金明細で、全員ぶんを確認して完了にする | — |

**設計の中心: AIは、お金と個人情報に直接触れない**

お金まわりを任せるとなると、「AIにお金を触らせて大丈夫か」が気になります。KUROKO は、**システムとしてはお金の仕事まで担いますが、AI（LLM）はお金に触れません**。だから安心して任せられます。これを、次の作りで保証しています。

- **AI（LLM）が担うのは、聞く・探す・提案する・説明する、まで。** 金額の計算、承認者と支払先の決定、署名、振込は、すべて決定論的なコードが行います。LLM のツールには、お金を動かすものがありません。
- **3つの鍵がそろわないと、振込は成立しない。** ①参加者本人の委任（上限額・支払先・期限）、②承認者による按分の承認、③銀行での本人の承認。
- **Policy Gate で二重に検査する。** 請求を出す側（按分があるか・承認があるか・承認者が規程どおりか・改ざんがないか・合計が合うか）と、支払う側（委任の上限・支払先・イベント・期限・署名・使用済みでないか）が、互いを信用せず別々に検査します。1円でも上限を超えれば、振込依頼は作られません。
- **状態を進めるのは事実だけ。** 「出欠が出そろった」「領収書を確定した」「入金を明細で確認した」という事実で、コードが次の段階に進めます。銀行の応答コードだけでは完了にせず、明細で確認できたときだけ完了にします。
- **インジェクションに多層で備える。** 参加者の自由記述は、ツールを持たない別のエージェント（隔離抽出）が、決まった語彙にだけ落とします。エージェントへの入口と出口は Agent Gateway を通します。

### アーキテクチャ説明

**全体の構成**

```
幹事（Web）─ Firebase Hosting ─ kuroko-dashboard（Next.js / Cloud Run）─┐
参加者（Slack）─ kuroko-gateway（署名検証・3秒Ack / Cloud Run）─ Cloud Tasks ─┤
                                                                            ▼
                                              kuroko-api（FastAPI / Cloud Run）
                                              按分・Policy Gate・状態の進行・MCP サーバー
                                                │                     │
                    Agent Gateway（入口。Model Armor）               請求（KMS で署名）
                                │                                     ▼
              Agent Runtime: kuroko-agent（統括）          payment-api（Cloud Run）
              Agent Runtime: extract-agent（隔離抽出）      AP2 の委任状・Policy Gate・入金確認
                                │                                     │
                    Agent Gateway（出口。許可した宛先だけ）            ▼
                                │                          bank-adapter（Cloud Run）
                                └─▶ kuroko-api の /mcp       口座とトークンはここだけ ─▶ 銀行API（sunabar）
```

**技術スタック**

| 区分 | 採用したもの |
|---|---|
| AIエージェント | Agent Development Kit（ADK）、Gemini Flash、Agent Platform の Agent Runtime（エージェント2つ） |
| エージェントの統制 | Agent Gateway（入口・出口）、Model Armor、Agent Registry（MCP サーバーの登録）、エージェントごとの identity |
| アプリケーション | Cloud Run 5サービス（FastAPI ×4、Next.js ×1）、Cloud Tasks、Cloud Scheduler |
| データ・鍵 | Firestore（用途ごとにデータベースを分離）、Cloud Storage、Cloud KMS（署名鍵）、Secret Manager |
| 認証 | Firebase Authentication（Google ログイン）、サービス間は ID トークンで呼び出し元を検査 |
| 支払い | AP2（Agent Payments Protocol）の委任状、銀行API（GMOあおぞらネット銀行の sunabar） |
| 外部サービス | Slack（出欠・委任・承認）、駅すぱあと（経路）、Google Maps（店の検索） |
| 基盤 | Terraform、GitHub Actions（Workload Identity Federation。鍵ファイルを発行しない） |

**設計上の工夫**

1. **エージェントと決定論的なコードを、デプロイ単位で分けた。** エージェントは Agent Runtime、金額・鍵・外部APIを扱うコードは Cloud Run に置きます。エージェントは、`kuroko-api` が公開する MCP のツールだけを使います。公開するのは「LLM が呼んでよい」ツールだけで、按分の確定・承認・振込のツールはそこにありません。

2. **支払いの権限を、3つのサービスに分けた。** 請求を作る `kuroko-api`、委任状を検証して振込を依頼する `payment-api`、銀行と話す `bank-adapter` です。口座番号とアクセストークンは `bank-adapter` の中だけにあり、ほかのサービスにも LLM にも出ません（仮名の ID だけが流れます）。請求は KMS の鍵で署名し、`payment-api` は請求側を信用せずに再検査します。

3. **AP2 の委任状を、銀行振込につないだ。** 参加者は Slack で「上限額・支払先・期限」つきの委任に同意します。支払い時は、その範囲に絞った委任状を作り、鎖として検証してから振込を依頼します。AP2（v0.2）が正式に対応する支払い手段はカードで、銀行振込への接続は公式サンプルの範囲外の独自実装です。

4. **エージェントの出入口を Gateway に通し、宛先を絞った。** エージェントへの入口は Agent Gateway と Model Armor を通します。エージェントからの出口は、アクセスポリシーで許可した宛先（自分たちの MCP サーバー）だけに絞り、それ以外の通信は拒否されることを実機で確かめました。エージェントごとに identity を分け、隔離抽出のエージェントにはツールも余分な権限も与えていません。

5. **二重実行と取りこぼしに備えた。** Slack のイベントは3秒以内に受け付けて Cloud Tasks に流し、処理は冪等にしています。支払いの識別子は「イベント × 支払う人」から決まるので、再送しても二重の振込になりません。銀行に Webhook がないため、承認の状況はポーリングで確かめ、10分で期限が切れた依頼は作り直します（最大2回）。

**実装の範囲（正直に書く）**

- **銀行は sunabar（サンドボックス）で、資金は仮想です。** 実際のお金は動きません。ただし、振込依頼・振込ごとの本人承認・入出金明細の照会は、本物の銀行APIの仕様どおりに実装しています。
- **デモでは、Slack と銀行で実際に操作する人は2人です。** ストーリーの参加者は10人（振込をするのは7人）ですが、7口座ぶんを口座ごとにログインし直して承認するのはデモの場で現実的でないため、Slack に実在する2人（一般の社員と、承認者の部長）だけが、Slack で同意・承認し、銀行で自分の振込を承認します。ほかの5人は、出欠と委任の同意をデモ用の代行が行い、振込は銀行の窓口のサービス（`bank-adapter`）が承認済みとして代行します。**委任状の署名と検証、Policy Gate、請求の署名、明細での入金確認は、全員ぶんが同じコードで動きます。** 按分の承認は代行しません。設定を空にすれば、全員の振込が実機になります。
- **審査員が1人で体験できるよう、Web に3人ぶんのチャット画面を並べています。** 審査員は Slack と銀行に入れないため、体験用のイベントに限り、参加者・承認者に届くカード（Slack に届くものと同じ）を、Web の画面からも押せます。銀行での承認は、体験用のボタンで代えています（本物の銀行には送りません）。**本来は、お金の権限に触れる操作（委任・承認）は、本人が Slack で行い、振込は本人が銀行で承認します。** Web から押した操作は、Slack の操作と区別して記録し、体験用でないイベントでは受け付けません。
- **本番化には、制度面の確認が要ります。** 参加者の依頼で振込の指図を銀行に伝える事業は、銀行法の電子決済等代行業の登録（または登録事業者との提携）が必要とされます。法的な判断は専門家への確認が必要です。参加者の署名鍵は、本番では本人の端末（パスキーなど）に置く想定です（いまはサーバー側の KMS で管理）。
- **規程と記憶の実装の範囲。** 規程は、架空の規程の文書（全12条）です。エージェントは、規程に関わることを聞かれると、自分の判断でツールを呼んで文書を調べ、条番号を添えて答えます。ツールは、文書を条ごとに検索して、合う条だけを返します（検索は自前のコードで、RAG Engine は使っていません）。按分に使う値は、検索で見つけた条だけを Gemini に渡して読み取り、コードが型と範囲で検証してから使います。チームの宴会実績は、幹事が Web で確認した定型の文だけを、Agent Platform の Memory Bank に保存し、次の企画で同じ店が候補に出たときに、順位の調整と理由に使います（読み書きはコードが行います。エージェントが記憶を直接読む形にはしていません）。
- **今後の実装:** エージェントが Memory Bank を直接読んで質問や説明に使うこと、開催前のリマインド、経費精算の書類の出力。

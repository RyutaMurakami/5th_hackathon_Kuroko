## プロジェクト概要

（200〜300文字。下の文は 240 文字）

飲み会の幹事は、出欠の確認・店探し・予約・立替・規程に沿った按分・集金と、仕事の合間にやることが山ほどあり、幹事の63.7%が「幹事残業」を経験しています。KUROKOは、その幹事業務を裏方から支えるAIエージェントです。要所の承認は人（幹事・参加者）が行い、面倒なところはKUROKOが代行します。依頼から出欠と支払いの委任を集め、開催希望駅から全員が行きやすい店を提案し、領収書を読み取って規程に沿って按分。承認と委任の範囲内で銀行APIの振込を実行し、入金確認まで担います。

## プロジェクト紹介

### 課題と解決

**現状の課題: 多くの社会人は、飲み会の幹事で苦労している！**

会社の飲み会の幹事を任されると、仕事の合間にやることがたくさんあります。

- 出欠の確認
- 適切な店探し
- 予約
- 当日の立替
- 会社やチームのルールに沿った按分計算
- 参加者からの集金
- etc…

**実際に、多くの社会人が苦労している現状**

- **幹事をやりたくない理由の51.5%が「面倒だから」**（出典: https://news.livedoor.com/article/detail/29958948/）
- **幹事の63.7%が「幹事残業」を経験**（カシキル「幹事残業」に関する調査・2018年6月。出典: https://kasikiru.com/column/?p=46）

既存の割り勘・集金サービスは、集金と領収書が中心です。金額は幹事が決めて入力します。規程に沿った判断と、承認の証跡までは担いません。

**そこで: 幹事業務をAIエージェントが支える仕組みが欲しい！**

**解決: KUROKOは、あなたの幹事業務を裏方から支えます**

- **要所での承認は、幹事または参加者（＝人間）が行います。**
- **面倒なところは、KUROKO（＝AIエージェント）が代行します。**

| 段階 | KUROKO（AIエージェント）が代行すること | 人が行う承認 |
|---|---|---|
| 1. 依頼 | チャットで依頼を受け、出欠と支払いの委任を集める | 参加者が、出欠と「上限額・支払先・期限つきの委任」に同意する |
| 2. 提案 | 幹事・参加者の開催希望駅から、全員が行きやすい場所・店の候補を理由つきで提示する（駅すぱあとAPI・Google Maps API を利用） | 幹事が店を選び、予約する（予約の代行はしない） |
| 3. 按分 | 領収書を読み取り、会社の規程に沿って支払額を計算する | 幹事が読み取り結果を確かめて確定する |
| 4. 承認・振込 | 承認者の承認と各自の委任の範囲内で、銀行APIに振込を依頼する（AP2 と sunabar を利用） | 承認者が按分を承認し、本人が銀行で振込を承認する |
| 5. 完了 | 幹事口座の明細で入金を確認し、振り返りを保存する | — |

### アーキテクチャ説明

**技術スタック**

| 区分 | 採用したもの |

| Gemini の使いどころ | 統括エージェントと隔離抽出エージェントの推論／領収書・予約画面・規程の文書からの値の読み取り（出力はコードが型と範囲で検証）。いずれも同じモデルを使用 |
| エージェントの統制 | Agent Gateway（入口・出口）、Model Armor、Agent Registry、エージェントごとの identity |
| アプリケーション | Cloud Run、Cloud Tasks、Cloud Scheduler |
| データ・鍵 | Firestore（用途ごとにデータベースを分離）、Cloud Storage、Cloud KMS（署名鍵）、Secret Manager |
| 認証 | Firebase Authentication（Google ログイン）、サービス間は ID トークンで呼び出し元を検査 |
| 支払い | AP2（Agent Payments Protocol）の委任状、銀行API（GMOあおぞらネット銀行の sunabar） |
| 外部サービス | Slack（出欠・委任・承認・幹事の操作）、駅すぱあと（経路・全員が行きやすい駅）、Google Maps（店の検索） |
| 基盤 | Terraform、GitHub Actions（Workload Identity Federation。鍵ファイルを発行しない） |

**設計上の工夫・アピールポイント（3つ）**

KUROKO が目指したのは、デモで動くだけではなく、**実運用に耐える AI アプリケーション**です。お金と個人情報を扱う業務を AI に任せるために、「誰が決めるのか」「何が決めるのか」を、仕組みとして分けました。

**1. 人間の承認と、AI エージェントが自動で実行する処理を分けた**

「要所は人、面倒なところは AI」を、運用の約束ではなく、仕組みで守ります。

| 人間が行う（承認・同意） | AI エージェント（とコード）が自動で行う |
|---|---|
| 参加者本人の、支払いの委任（上限額・支払先・期限）への同意 | 依頼の整理、店の提案と理由の説明 |
| 承認者による、按分の承認 | 領収書の読み取り、規程に沿った按分の計算 |
| 参加者本人の、銀行での振込の承認 | 委任の範囲の検査、請求の署名、振込の依頼、明細での入金確認 |

- **3つの鍵がそろわないと、振込は成立しません。** ①参加者本人の委任、②承認者による按分の承認、③銀行での本人の承認。どれか1つでも欠ければ、AI がどれだけ「やって」と言われても、振込依頼は作られません。
- **委任は AP2 の委任状で表します。** 参加者は Slack で「上限額・支払先・期限」つきの委任に同意します。支払い時は、その範囲に絞った委任状を鎖として検証してから、銀行に振込を依頼します。AP2（v0.2）が正式に対応する支払い手段はカードで、銀行振込への接続は公式サンプルの範囲外の独自実装です。
- **請求側と支払い側が、互いを信用せず別々に検査します（Policy Gate）。** 按分があるか・承認があるか・承認者が規程どおりか・改ざんがないか・合計が合うか、委任の上限・支払先・期限・署名・使用済みでないか。1円でも上限を超えれば、振込依頼は作られません。
- **状態を進めるのは事実だけ。** 「出欠が出そろった」「領収書を確定した」「入金を明細で確認した」という事実で、コードが次の段階に進めます。銀行の応答コードだけでは完了にしません。

**2. LLM が判断するところと、関数的に処理するところを、Tool と Callback で分けた**

LLM は「聞く・探す・選ぶ・説明する」だけを担い、計算・検査・許可は、決まった関数（コード）が行います。その境目を、Tool と Callback の2つで実装しています。

- **Tool: LLM が呼べるのは、4つだけ。返ってくるのは、コードが決めた事実。** 規程の検索・店の検索・予算の確認・イベントの概要の4つで、すべて `kuroko-api` が MCP で公開するコードです。足切りと順位づけ、条の特定、上限の判定はツールの中のコードが行い、LLM はそれを言葉にするだけです。**金額の計算・承認・署名・振込のツールは、そもそも存在しません。**
- **Callback: ツールを呼ぶ直前に、コードが許可リストで止める。** ADK の `before_tool_callback` が、許可した4つ以外の呼び出しを、LLM の判断に関わらず止めます（ツールの絞り込みと合わせた二重の防御）。プロンプトで「やらないで」とお願いするのではなく、関数が止めます。
- **読み取りの結果も、コードが検証する。** 領収書・予約画面・規程の読み取りは Gemini が行い、出力はコードが型と範囲で検査してから使います。外れたら既定の値に戻します。
- **自由記述は、ツールを持たない別のエージェントが語彙に落とす。** 参加者の苦手な食べ物などの原文は、統括エージェントに渡しません（隔離抽出）。

**3. エージェントの出入口を Gateway に通し、宛先を絞った**

エージェントへの入口は Agent Gateway と Model Armor を通し、プロンプトインジェクションを検査します。エージェントからの出口は、アクセスポリシーで許可した宛先（自分たちの MCP サーバー）だけに絞り、それ以外の通信は拒否されることを実機で確かめました。エージェントごとに identity を分け、隔離抽出のエージェントにはツールも余分な権限も与えていません。口座番号とアクセストークンは `bank-adapter` の中だけにあり、ほかのサービスにも LLM にも出ません（仮名の ID だけが流れます）。

**この3つで、AI を「お金まわりの実務」に使える形にしました。** 人の承認、コードの検査、Gateway の統制が、それぞれ独立して働くので、LLM が間違えても、お金は動きません。

**実装の範囲（正直に書く）**

- **銀行は sunabar（サンドボックス）で、資金は仮想です。** 実際のお金は動きません。ただし、振込依頼・振込ごとの本人承認・入出金明細の照会は、本物の銀行APIの仕様どおりに実装しています。
- **デモでは、Slack と銀行で実際に操作するのは3人です。** ストーリーの参加者は10人（振込をするのは7人）ですが、7口座ぶんを口座ごとにログインし直して承認するのはデモの場で現実的でないため、実演では、**幹事（Slack の DM で、お店選び・予約画面や領収書の画像の送信・各確認を行う）**と、Slack に実在する**一般の社員と承認者の部長**の3人が、Slack で操作し、銀行で自分の振込を承認します。ほかの参加者は、出欠と委任の同意をデモ用の代行が行い、振込は銀行の窓口のサービス（`bank-adapter`）が承認済みとして代行します。開催希望駅を聞くのも、この3人だけです（店の候補は、この3人の希望から、駅すぱあとで全員が行きやすい駅を計算して探します）。**委任状の署名と検証、Policy Gate、請求の署名、明細での入金確認は、全員ぶんが同じコードで動きます。** 按分の承認は代行しません。設定を空にすれば、全員の振込が実機になります。
- **審査員が1人で体験できるよう、Web に3人ぶんのチャット画面を並べています。** 審査員は Slack と銀行に入れないため、体験用のイベントに限り、参加者・承認者に届くカード（Slack に届くものと同じ）を、Web の画面からも押せます。銀行での承認は、体験用のボタンで代えています（本物の銀行には送りません）。**本来は、お金の権限に触れる操作（委任・承認）は、本人が Slack で行い、振込は本人が銀行で承認します。** Web から押した操作は、Slack の操作と区別して記録し、体験用でないイベントでは受け付けません。実演用の Web 画面は、進み具合と、KUROKO が参照している記憶・会社の規程（Memory Bank と按分ルール）を映す画面です。
- **本番化には、制度面の確認が要ります。** 参加者の依頼で振込の指図を銀行に伝える事業は、銀行法の電子決済等代行業の登録（または登録事業者との提携）が必要とされます。法的な判断は専門家への確認が必要です。参加者の署名鍵は、本番では本人の端末（パスキーなど）に置く想定です（いまはサーバー側の KMS で管理）。
- **規程と記憶の実装の範囲。** 規程は、架空の規程の文書（全12条）です。エージェントは、規程に関わることを聞かれると、自分の判断でツールを呼んで文書を調べ、条番号を添えて答えます。ツールは、文書を条ごとに検索して、合う条だけを返します（検索は自前のコードで、RAG Engine は使っていません）。按分に使う値は、検索で見つけた条だけを Gemini に渡して読み取り、コードが型と範囲で検証してから使います。チームの宴会実績は、幹事が Web で確認した定型の文だけを、Agent Platform の Memory Bank に保存し、次の企画で同じ店が候補に出たときに、順位の調整と理由に使います（読み書きはコードが行います。エージェントが記憶を直接読む形にはしていません）。
- **今後の実装:** エージェントが Memory Bank を直接読んで質問や説明に使うこと、開催前のリマインド、経費精算の書類の出力。

## プロジェクト概要（200〜300文字。240文字）

飲み会の幹事は、出欠の確認・店探し・予約・立替・規程に沿った按分・集金と、仕事の合間にやることが山ほどあり、幹事の63.7%が「幹事残業」を経験しています。KUROKOは、その幹事業務を裏方から支えるAIエージェントです。要所の承認は人（幹事・参加者）が行い、面倒なところはKUROKOが代行します。依頼から出欠と支払いの委任を集め、開催希望駅から全員が行きやすい店を提案し、領収書を読み取って規程に沿って按分。承認と委任の範囲内で銀行APIの振込を実行し、入金確認まで担います。

## 課題と解決（800文字以内。602文字）

■現状の課題：多くの社会人は、飲み会の幹事で苦労している！
会社の飲み会の幹事を任されると、仕事の合間にやることがたくさんあります。
- 出欠の確認
- 適切な店探し
- 予約
- 当日の立替
- 会社のルールに沿った按分計算
- 参加者からの集金

▼実際に、苦労している人は多い
- **幹事をやりたくない理由の51.5%が「面倒だから」**（https://news.livedoor.com/article/detail/29958948/）
- **幹事の63.7%が「幹事残業」を経験**（カシキル・2018年6月 https://kasikiru.com/column/?p=46）

既存の割り勘・集金サービスは集金が中心で、規程に沿った判断と承認の証跡までは担いません。

■解決：KUROKOは、あなたの幹事業務を裏方から支えます
**要所での承認は、幹事または参加者（人間）。面倒なところは、KUROKO（AIエージェント）が代行します。**
▼1. 依頼：チャットで依頼。出欠と支払いの委任を収集
▼2. 提案：開催希望駅から、全員が行きやすい店を提示（駅すぱあと・Google Maps）
▼3. 按分：領収書を読み取り、会社の規程に沿って支払額を計算
▼4. 承認・振込：人が確認し、銀行APIで実行（AP2・sunabar）
▼5. 完了：入金を明細で確認し、振り返りを保存

## アーキテクチャ説明（800文字以内。724文字）

■技術スタック
- AIエージェント：ADK、Gemini 3.8 Flash（gemini-3.8-flash）、Agent Runtime、Memory Bank
- 統制：Agent Gateway（入口・出口）、Model Armor、Agent Registry
- アプリ：Cloud Run、Cloud Tasks、Cloud Scheduler
- データ・鍵：Firestore、Cloud Storage、Cloud KMS、Secret Manager
- 認証・支払い：Firebase Authentication、AP2、sunabar（銀行API）
- 外部：Slack、駅すぱあと、Google Maps
- 基盤：Terraform、GitHub Actions

■設計上の工夫：実運用に耐えるAIアプリケーションへ
▼1. 人間の承認と、AIの自動実行を分けた
本人の委任（AP2の委任状）・承認者の承認・銀行での本人承認の3つがそろわない限り、振込は成立しません。請求側と支払い側は、互いを信用せず別々に検査します（Policy Gate）。
▼2. LLMの判断と、関数的な処理を、ToolとCallbackで分けた
LLMが呼べるToolは4つだけで、返すのはコードが決めた事実です。金額計算・承認・署名のToolは存在しません。許可外の呼び出しは、before_tool_callbackが関数として止めます。
▼3. 出入口をGatewayに通した
入口はModel Armorで検査し、出口は許可した宛先だけに通します。エージェントごとにidentityを分け、口座とトークンはLLMに出しません。

## 補足（フォームには貼らない）

### 実装の範囲（正直に書く。README・デモ動画の説明に使う）

- **銀行は sunabar（サンドボックス）で、資金は仮想です。** 実際のお金は動きません。ただし、振込依頼・振込ごとの本人承認・入出金明細の照会は、本物の銀行APIの仕様どおりに実装しています。
- **デモでは、Slack と銀行で実際に操作するのは3人です。** ストーリーの参加者は10人（振込をするのは7人）ですが、7口座ぶんを口座ごとにログインし直して承認するのはデモの場で現実的でないため、実演では、**幹事（Slack の DM で、お店選び・予約画面や領収書の画像の送信・各確認を行う）**と、Slack に実在する**一般の社員と承認者の部長**の3人が、Slack で操作し、銀行で自分の振込を承認します。ほかの参加者は、出欠と委任の同意をデモ用の代行が行い、振込は銀行の窓口のサービス（`bank-adapter`）が承認済みとして代行します。開催希望駅を聞くのも、この3人だけです（店の候補は、この3人の希望から、駅すぱあとで全員が行きやすい駅を計算して探します）。**委任状の署名と検証、Policy Gate、請求の署名、明細での入金確認は、全員ぶんが同じコードで動きます。** 按分の承認は代行しません。設定を空にすれば、全員の振込が実機になります。
- **審査員が1人で体験できるよう、Web に3人ぶんのチャット画面を並べています。** 審査員は Slack と銀行に入れないため、体験用のイベントに限り、参加者・承認者に届くカード（Slack に届くものと同じ）を、Web の画面からも押せます。銀行での承認は、体験用のボタンで代えています（本物の銀行には送りません）。**本来は、お金の権限に触れる操作（委任・承認）は、本人が Slack で行い、振込は本人が銀行で承認します。** Web から押した操作は、Slack の操作と区別して記録し、体験用でないイベントでは受け付けません。実演用の Web 画面は、進み具合と、KUROKO が参照している記憶・会社の規程（Memory Bank と按分ルール）を映す画面です。
- **本番化には、制度面の確認が要ります。** 参加者の依頼で振込の指図を銀行に伝える事業は、銀行法の電子決済等代行業の登録（または登録事業者との提携）が必要とされます。法的な判断は専門家への確認が必要です。参加者の署名鍵は、本番では本人の端末（パスキーなど）に置く想定です（いまはサーバー側の KMS で管理）。
- **規程と記憶の実装の範囲。** 規程は、架空の規程の文書（全12条）です。エージェントは、規程に関わることを聞かれると、自分の判断でツールを呼んで文書を調べ、条番号を添えて答えます。ツールは、文書を条ごとに検索して、合う条だけを返します（検索は自前のコードで、RAG Engine は使っていません）。按分に使う値は、検索で見つけた条だけを Gemini に渡して読み取り、コードが型と範囲で検証してから使います。チームの宴会実績は、幹事が Web で確認した定型の文だけを、Agent Platform の Memory Bank に保存し、次の企画で同じ店が候補に出たときに、順位の調整と理由に使います（読み書きはコードが行います。エージェントが記憶を直接読む形にはしていません）。
- **今後の実装:** エージェントが Memory Bank を直接読んで質問や説明に使うこと、開催前のリマインド、経費精算の書類の出力。

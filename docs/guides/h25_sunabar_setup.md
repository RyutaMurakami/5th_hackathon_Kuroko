- ラベル（`acct01`〜`acct10`）は KUROKO の中での呼び名。**口座番号ではない**ので、コード・文書に書いてよい
- sunabar ポータルの口座の並び順と、ラベルの対応は**あなたが決めて、手元のメモにだけ残す**（口座番号は書かない。ポータルの表示名や順番で覚えればよい）
- **残高を確認する**: 振込元の7口座には、上の金額以上の残高が要る（デモを何度か繰り返すなら、その回数ぶん）。sunabar では口座間の振替で仮想の資金を動かせる。足りなければポータル／サービスサイトで補充する

## 2. トークンを Secret Manager に登録する（⌨ あなた。P3）

**トークンはチャットに貼らない**。手元で JSON を作って、そのまま Secret Manager に入れる。

1. sunabar ポータルにログインし、「sunabarサービスサイトで使える銀行口座」を開く
2. 手元で次のファイルを作る（`sandbox/` は git の管理外）。各口座の「トークン情報（コピー）」の値を貼る

   ```bash
   mkdir -p sandbox/sunabar
   cat > sandbox/sunabar/tokens.json <<'EOF'
   {
     "acct01": "ここに acct01 のトークン",
     "acct02": "ここに acct02 のトークン",
     "acct03": "...",
     "acct04": "...",
     "acct05": "...",
     "acct06": "...",
     "acct07": "...",
     "acct08": "...",
     "acct09": "...",
     "acct10": "..."
   }
   EOF
   ```

3. 登録して、手元のファイルを消す

   ```bash
   gcloud secrets versions add sunabar-tokens --data-file=sandbox/sunabar/tokens.json --project=kuroko-509311
   rm sandbox/sunabar/tokens.json
   ```

4. 登録できたら、AI に「登録した」とだけ伝える（AI は `gcloud secrets versions list sunabar-tokens` で版があることだけを確認する）

> **`sunabar-client`（クライアント情報）は使わない**。sunabar には OAuth の認可の流れがないため。入れ物は残しておき、本番化の論点（SPEC 8.9）として説明に使う。不要と確定したら I3 の Terraform から外す。

## 3. 承認に使うもの（🖱 あなた）

- 振込の承認は、**sunabar サービスサイト**にログインし、「お知らせ」の振込承認の通知 → 承認ページ → **取引パスワード**（サンドボックスでは任意の文字列でよいとの報告あり。review 04）で行う
- サービスサイトへのログイン方法と、承認の画面までの道筋を、手順4の前に一度確かめておく（承認の期限は約10分）

AI が `sandbox/sunabar/smoke.py` を用意し、**あなたの承認を得てから**次の順に実行する。トークンは Secret Manager から読み、画面には口座番号を末尾4桁までしか出さない。

| 段階 | AI がすること | あなたがすること | 確かめること（V10） |
|---|---|---|---|
| 4-1 照会だけ | 10口座それぞれで `/accounts`・`/accounts/balances` を呼ぶ | — | 10個のトークンが有効か。ラベルと名義・残高の対応が合っているか（②） |
| 4-2 振込1件 | `acct08`（加藤）→ `acct01`（高橋）に **1円**の振込依頼 | サービスサイトで承認する | 依頼 → 承認 → `transferStatus = 20` → 幹事の入金明細に出る、が一通り動くか（①）。応答の項目名（`applyNo` など）と、振込の付加情報に `payment_id` を載せられるか（V14⑤） |

### 4-0. 振込依頼 API で分かったこと（2026-10-06。AI が実機で確認。V10 に書き戻す）

| 項目 | 内容 |
|---|---|
| 銀行コード | **`0310`**（公式サンプルの `0398` は通らない。「振込先金融機関の支店を正しく入力してください」になる）。銀行名カナ `ｱｵｿﾞﾗ`、支店は口座情報の `branchCode`（301・302）と半角カナ `ｳﾐ`・`ﾆｼﾞ` |
| 口座番号 | **7桁**（先頭の 0 を含む。5桁は `WG_ERR_110`） |
| 応答 | 受付は **HTTP 201**、`resultCode: "2"`、`applyNo`（振込申請番号）。**200 だけを成功とみなすと誤判定する** |
| 状況照会 | `GET /transfer/status?accountId=&queryKeyClass=1&applyNo=`（`queryKeyClass=2` は申請番号を指定できない）。**承認前は 0件で返る**ので、`bank-adapter` は「0件＝承認待ちか期限切れ」として扱い、承認後の `transferStatus` と、入金明細の両方で確認する（SPEC 6.3） |
| 冪等キー | 仕様書上は振込依頼のヘッダー `Idempotency-Key` に対応するが、**実測（2026-10-06）では、同じキーで再送しても別の `applyNo` が振られた（重複を防がない）**。**`bank-adapter` が自分で冪等を担保する**: `idempotency_key` → `applyNo` の対応を Firestore（`bank`）に先に書き、同じキーなら銀行を呼ばずに保存済みの `applyNo` を返す（書き込みと送信の順序は、書いてから送り、失敗時は照会で確認）。キーは念のため銀行にも渡す |
| 結果コード | `1`=完了、`2`=未完了（承認待ち）。`applyEndDatetime` は完了のときだけ付く |
| 項目の制約 | 1件なら `totalCount`・`totalAmount` は省略可（2件以上は一括振込扱い）。`remitterName` は半角48文字まで（省略時は口座名義） |
| 入金明細 | 項目は `transactionDate`・`valueDate`・`transactionType`・`amount`・`remarks`・`balance`・`itemKey` だけ。**振込元の口座番号は出ない**。`remarks` は **`振込 ` ＋ 振込依頼人名**（実測。`remitterName` を省略すると口座名義＝人ごとに別の名前。全角カナで出る）。出金側の `remarks` は受取人名 |
| **付加情報には載せられない** | **`applyComment` は銀行で読み捨て**。SPEC 13章・V14⑤ の「付加情報に `payment_id` を載せて明細を照合する」は成り立たない。**確定した方針（2026-10-06）**: ①**完了の判定**＝幹事の入金明細で、**金額＋`remarks` の振込依頼人名＋日付**が合う入金（振込元の口座は出ないが、**人ごとに名義が違う**ので、名前で振込元を区別できる）。② 追跡＝`transferRequestKey`（`payment_id` から決めた UUID）と状況照会の `transferStatus = 20`（`transferRequestKey` が照会に返るかは未確認）。③ 補助＝`remitterName` に識別子を載せる案は、**カスタム値が `remarks` に出るか未確認**（次の疎通で確かめる）。同じ人が同じ日に同額を2回払う場合だけ区別できない（イベントでは起きない） |
| ログ | sunabar ポータルに、API のリクエスト・レスポンスのログ画面がある（トークンも表示されるので、貼るときはボディだけにする） |

### 4-1b. 実測の結果（2026-10-06）

- **照会**: 10口座すべてで有効。ラベルとポータルの番号が一致
- **V10 ① 依頼 → 承認 → 状況確認 → 明細**: **動いた**。`acct03` から 1円（幹事 `acct01` 宛）と 10,000円×6 を依頼し、あなたがサービスサイトで承認 → `transferStatus = 20`（手続済）、手数料 0円、受取側の明細に入金が出た。残高は `acct01`=1円、`acct02`・`acct04`〜`acct08`=10,000円、`acct03`=240,009円（`acct09`・`acct10` は 0円）
- **冪等キー**: 重複を防がない（上の表）
- **残り**: 期限切れの挙動（4-3。放置した1円の依頼3件 `…029`・`…031`・`…033` で確かめる。**承認しないこと**）、`transferRequestKey` の返り方、カスタム `remitterName` の明細での見え方、Cloud Run からの疎通（4-4）

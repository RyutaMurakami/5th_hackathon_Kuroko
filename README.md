# KUROKO — 飲み会の幹事を、舞台裏で引き受ける AI エージェント

会社の歓送迎会の幹事の仕事（出欠、店探し、予約の確認、割り勘の計算、承認の取り付け、集金、振り返り）を、AI エージェントが引き受けます。**AI が担うのは、聞く・探す・調べる・説明することだけ**です。金額の計算、可否の判断、署名、振込は、決まった手順のコードと、本人の操作が担います。

Google Cloud の AI エージェントのハッカソン（第5回）の提出作品です。動作確認の方法は、提出フォームの「動作確認の方法」に記載しています。

## 課題と、KUROKO のアプローチ

幹事を任されると、仕事の合間に、出欠の確認・店探し・予約・当日の立替・会社のルールに沿った按分・集金と、やることが山ほどあります。幹事をやりたくない理由の51.5%が「面倒だから」、幹事の63.7%が「幹事残業」を経験している、という調査があります（[出典1](https://news.livedoor.com/article/detail/29958948/)・[出典2](https://kasikiru.com/column/?p=46)）。

既存の割り勘・集金サービスは、集金と領収書が中心です。金額は幹事が決めて入力し、**規程に沿った判断と、承認の証跡までは担いません。**

KUROKO は、要所の承認は人（幹事・参加者）が行い、面倒なところは AI エージェントが代行する形で、幹事の仕事を裏方から支えます。

| 段階 | KUROKO（AI エージェント）がすること | 人がすること |
|---|---|---|
| 1. 依頼 | チャットで依頼を整理し、足りないことだけを聞く。規程を聞かれたら、文書を調べて答える | 幹事が計画を確かめて確定する |
| 2. 出欠・委任 | 参加者に、出欠と、上限つきの支払いの委任を依頼する | 参加者が同意する（委任状への署名のきっかけは、本人の操作だけ） |
| 3. 提案 | 開催希望駅から、全員が行きやすい駅を探し、店を提案する。理由と、過去の実績を添える | 幹事が選び、予約する |
| 4. 按分 | 予約画面・領収書を読み取り、規程に沿って按分する | 幹事が読み取り結果を確かめて確定する。承認者が按分を承認する |
| 5. 承認・振込 | 委任の範囲内で振込を依頼し、銀行の明細で入金を確認する | 参加者が、銀行で振込を承認する |
| 6. 完了 | 満足度を集め、実績と合わせて、次回に覚える内容をまとめる | 幹事が確かめて、覚えさせるかを決める |

## AI とコードの役割の境界

これ自体を、最大の安全策にしています。

- **AI が決めないもの**: 金額の計算、承認者、支払先、規程の変更、委任状への署名、店の順位、振込の作成、「完了」の判断
- **AI が見ないもの**: 実名（画面の表示を除く）、口座番号、銀行のトークン、署名鍵、個人ごとの回答
- **お金が動くには、3つの鍵がそろう必要があります**: ①参加者本人の委任（上限額・支払先・期限）、②承認者による按分の承認、③銀行での本人の承認
- **請求する側と支払う側が、互いを信用せず、別々に検査します**（Policy Gate）。委任の範囲を1円でも超える振込は、作られません。銀行の口座とトークンは、銀行の窓口の1か所だけが持ちます
- **AI が呼べるツールは4つだけ**（規程の検索・店の検索・予算の確認・イベントの概要）で、お金・承認・署名に当たるツールはありません。許可外の呼び出しは、コード（Callback）が止めます
- **AI の出入口は、Agent Gateway を通します**。入口は Model Armor で検査し、出口は許可した宛先だけに通します

## アーキテクチャ

![KUROKO の構成図](docs/diagrams/export/KUROKO_GoogleCloud構成図_v3.0.svg)

| 区分 | 役割 |
|---|---|
| Web の画面（Firebase、Cloud Run） | 幹事・審査員の画面。Google ログイン |
| Slack 受付API（Cloud Run） | Slack の入口。署名を検証して、タスクキューに渡すだけ |
| 業務API（Cloud Run） | 按分・Policy Gate・請求の署名・振り返り・記憶の読み書き。エージェント用のツール（MCP） |
| 支払いAPI（Cloud Run） | AP2 の委任状の署名と検証、振込の依頼、入金の確認、領収書の署名 |
| 銀行連携API（Cloud Run） | 銀行 API（sunabar）の窓口。口座とトークンは、ここだけ |
| 統括エージェント（Agent Runtime） | ADK・Gemini 3.8 Flash。ツールは、業務API の MCP の4つだけ |
| 隔離抽出エージェント（Agent Runtime） | 自由記述を、決まった語彙に落とすだけ（ツールなし） |
| Agent Platform | Agent Gateway（入口・出口）、Model Armor、Agent Registry、Memory Bank（チームの宴会実績の記憶） |
| データ・鍵 | Firestore、Cloud Storage、Cloud KMS、Secret Manager |
| 非同期 | Cloud Tasks、Cloud Scheduler |
| 外部 API | 駅すぱあと（全員が行きやすい駅・所要時間）、Google Maps（店の検索）、sunabar（銀行 API の実験環境） |

## 実装の範囲（正直に書きます）

- 銀行は sunabar（実験用の環境）で、**資金は仮想**です。ただし、振込依頼・振込ごとの本人承認・入出金明細の照会は、本物の銀行 API の仕様どおりに実装しています。
- デモ動画では、Slack と銀行を実際に操作するのは、幹事と、参加者・承認者の役の3人です。ほかの参加者の出欠・委任・振込は、デモ用の代行が行います。**委任状の署名と検証、Policy Gate、請求の署名、明細での入金確認は、全員ぶんが同じコードで動きます。**
- 審査員が1人で体験できるよう、体験用の画面では、参加者・承認者の操作と銀行の承認を、Web から行えます。本来は、本人が Slack と銀行で行う操作です。Web から行った操作は、区別して記録しています。
- 規程は、架空の文書（[policies/company_rules.md](policies/company_rules.md)）です。会社「株式会社Akakura」・登場人物も、すべて架空です。エージェントは、ツールで文書を条ごとに調べます（検索は自前のコードです）。
- 記憶は、Agent Platform の Memory Bank に、幹事が確かめた決まった形の文だけを保存します。読み書きはコードが行います。
- 本番で使うには、制度面の確認が要ります（参加者の依頼で振込の指図を銀行に伝える事業は、電子決済等代行業の登録などが必要とされます。法的な判断は、専門家への確認が必要です）。

設計の詳細は [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)、仕様は [docs/SPEC.md](docs/SPEC.md) にあります。

## 利用している OSS とライセンス

このリポジトリが直接使っている主なものです。

| 名前 | 使っている場所 | ライセンス |
|---|---|---|
| [Agent Payments Protocol（AP2）](https://github.com/google-agentic-commerce/AP2) の SDK | 支払いAPI（委任状の作成・検証、制約の検査） | Apache License 2.0 |
| [Agent Development Kit（ADK）](https://github.com/google/adk-python) | 統括エージェント・隔離抽出エージェント | Apache License 2.0 |
| [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk) | 業務API（エージェント用のツールの入口） | MIT License |
| [FastAPI](https://github.com/fastapi/fastapi)・[Pydantic](https://github.com/pydantic/pydantic) | 業務API・支払いAPI・銀行連携API | MIT License |
| [Next.js](https://github.com/vercel/next.js)・[React](https://github.com/facebook/react) | Web の画面 | MIT License |
| [Slack SDK for Python](https://github.com/slackapi/python-slack-sdk) | 業務API・支払いAPI | MIT License |

AP2 の SDK は、公式のリポジトリから取り込んでいます。AP2（v0.2）が正式に対応する支払い手段はカードで、銀行振込への接続は、公式のサンプルの範囲外の、このプロジェクト独自の実装です。
